# ワンカット

> 名称は仮称です（変更の可能性があります）。

> 本番反映の順序とロールバック手順は `docs/GROUP_PLAY_SETUP.md` の「本番反映の順序」「ロールバック手順」を参照してください（migration を本番に適用してからデプロイします）。

主演が「その一瞬の顔」だけで演じ、ほかの参加者が A〜F のお題から「どの瞬間か」を当てるゲームです（`game_type='one_cut'`、グループ同時プレイ専用）。写真・カメラ・録音は使わず、顔は対面で見るだけで記録しません。仕様の正は `docs/games/one-cut.md`、この文書は運用（保存範囲・migration の適用順・秘密保持）を記録します。今回実装したのは基本形（1人ずつ主演）です。F1スタートと全員同時撮影、1台回しは含みません。

## 遊び方

2〜8人で参加し、代表者がルームを作ります。代表者の端末は、テーブルの中央に置く「監督モニター」であり、代表者本人のプレイ端末でもあります。主演は 代表者 → 参加順 で1人ずつ交代し、テイク k の主演は `(k-1) % 人数` 番目です。周回数は作成時に1〜3周、または「おまかせ」（開始時に人数で決定。2〜4人は2周、5〜8人は1周）を選びます。

1. **お題の表示**: 全員の画面に A〜F の6つのお題を出します。主演の端末にだけ「あなたは C」と担当お題を出し、押している間だけ見える「長押し」にしています。主演は「準備OK」を押します（代表者が代わりに押せます）。主演は「このテイクはパス」も選べます（得点なし、理由は聞きません）。
2. **撮影**: 「シーン◯、テイク1」→「よーい…」→ 3・2・1 → 「アクション！」 → 3秒 → 「カット！」。主演はアクションの合図でお題の一瞬の顔をします（声と身ぶりは使いません）。
3. **投票**: 主演以外が A〜F から1つ選びます。「わからない（パス）」も選べます。全員が投票するか、カットから40秒の自動締切か、代表者の「締め切る」で終わります。
4. **正解公開**: 正解の記号とお題、記号ごとの票数、正解した人の名前、各自の得点を出します。誰が何に投票したかは出しません。続けて「◯◯さん、実際にこんな瞬間あった？」を表示し、主演か代表者が「次のシーンへ」を押します（入力欄はなく、話は保存しません）。
5. **区切り**: 全員が1回ずつ主演を終えると区切り画面です。そのラウンドの振り返りと、自分以外の主演1人への「いいね」（主演賞）を出します。代表者が「次のラウンドへ」を押すと、最多いいねの人（同数は全員）を「主演賞」として発表します。票数・順位・0票の人は出しません。2人プレイでは主演賞を出さず、得点は「ふたりで◯点」と表示します。
6. **オールアップ**: 全員の得点（順位・最下位の表現なし）と、各ラウンドの主演賞を出します（PO 決定で全員の得点表示は決定済み）。この画面のデータは終了から5分だけサーバーが返し、端末は受け取った画面をそのまま保持します。

### 得点

- 当てた人は1点、主演は当てた人数分です。「わからない」・未投票は0点、主演がパスしたテイクは全員0点です。
- 採点は `one_cut_score_take`（DB）で行い、表示用の内訳は `scoreSoloTake`（`dist/one-cut-rules.js`）で同じ規則から計算します。

## 代表者端末の操作（目隠しカバー）

代表者が主演のとき、または代表者が投票・いいねをするときは、共有画面の上に全画面の目隠しカバーを出し、代表者がスマホを手に取って操作します。カバーを閉じた監督モニターには、代表者の担当お題・投票先・いいね先を一切出しません（代表者の「投票済み」かどうかは投票数に含まれます）。APIは通常の参加 secret で動き、代表者専用のAPIはありません。カバーは、そのテイク・phase が進んだときに自動で閉じます。

## 撮影演出のタイミング

サーバーが `ready` を受けた時刻 S から、`take_started_at = S + 1.0秒`（T0）、`action_at = T0 + 5.5秒`、`cut_at = action_at + 3.0秒`、`vote_deadline = cut_at + 40秒` を決めて保存します（`one_cut_ready`。APIサーバーの時計を渡し、DBで ±15 秒の範囲を検証）。端末は、状態応答の `serverNow` と送受信時の `performance.now()` から `offset = serverNow − (送信 + 受信) / 2` を求め、直近5回のうち往復時間が最小のものを採用します（`dist/one-cut-timeline.js`）。各端末は 100ms ごとに `stageAt(take, 推定サーバー時刻)` で段階（standby / slate / yoi / 3・2・1 / action / cut / vote）を計算して描画するだけで、進行を端末が決めることはありません。遅れて取得した端末は、現在時刻に応じた段階から再生し、過ぎた音は鳴らしません。brief と take の間だけポーリングを500msにします（1参加者120回/分。上限180回/分の範囲内）。

`take` から `vote`、`vote` から `result` は遅延遷移です（カットの0.5秒後に投票画面、締切で採点して結果）。状態取得は `one_cut_state` の中で DB の時計により期限を判定して遷移させ、action 処理時は API が期限を見て `one_cut_expire` を呼びます。状態取得1回あたりのリクエストは、ルーム・参加者の取得3回と `one_cut_state` 1回の計4回です（以前は7〜18回）。`serverNow` は、リクエストを受け取った時刻で刻みます。

## 音

ビープ（880Hz・120ms）とカチンコ音（ノイズ＋低い打撃音。カット音も同じ音）は Web Audio で合成します。音源ファイルは追加していません（`docs/AUDIO_ASSETS.md` の録音・生成アセットの記録対象外）。

- 既定は代表者端末だけが鳴らし、参加者端末は右上の「音」で各自 ON にできます。保存キーは `localStorage` の `mingle.oneCut.sound`（保存できなくても動きます）。
- `AudioContext` はユーザー操作の中で解除します（代表者は「撮影開始」、音を ON にしたときのボタン、再読み込み後の最初のタップ）。解除後の音は `AudioContext.currentTime` 基準で先に予約し、`setTimeout` に頼りません。
- iOS の消音スイッチでは Web Audio が鳴らないことがあります。検出できない前提で、視覚演出（カウント数字、進捗リング、アクション時の背景色変更、カチンコ）だけで遊べます。Android Chrome の主演端末では、アクション時に `navigator.vibrate(200)` を使います。`prefers-reduced-motion` では動きを止めます。
- brief から vote の間は Screen Wake Lock を機能検出して要求します（失敗しても無視）。

## 入口

通常利用では、質問テーマ一覧のゲーム棚にある「ワンカット（2〜8人）」からルームを作ります。ルーム作成にはログインが必要で、未ログインなら `/?oneCutAuth=1` を経由してログイン後に作成へ戻ります。店舗利用では、卓上QRの店舗ランディングのゲーム入口から作成し、店舗トークンはルーム作成時に検証されます。参加者の参加と操作にはログインを要求しません。

## 状態遷移

```
lobby -(start: 代表者)-> brief(1)
brief -(ready: 主演/代表者)-> take -(cut_at + 0.5秒: 遅延遷移)-> vote
brief -(skip: 主演/代表者, 1回のRPCで skipped と次テイクの作成)-> brief(k+1)  / ラウンド最後なら break
vote -(全員投票 / vote_deadline / close_vote)-> result（採点）
result -(next: 主演/代表者)-> brief(k+1) / ラウンド最後のテイクなら break
break -(continue: 代表者, 主演賞を集計)-> brief(次ラウンドの最初) / 最終ラウンドなら final
どの phase からでも finish(代表者) -> final（room.status = 'ended'）
```

ゲームが終わる経路は2つ（`finish` と、最終ラウンドの `continue`）あり、どちらも内部関数 `one_cut_finalize` を通ります。`one_cut_finalize` は全員の得点と主演賞だけを `one_cut_results` に5分分コピーし、ゲームの行（お題・テイク・投票・いいね・得点・主演賞）をすべて削除します。ロビーで終えたゲームは結果も残しません。`final` は DB の phase ではなく、`one_cut_results` から作る表示状態で、5分後は `ended` の最小応答になります。

## サーバー側の秘密保持

- 状態は1回のRPC `one_cut_state(p_room_id, p_member_id)` が、呼び出した本人向けにフィルタ済みの一貫したスナップショットとして返します（APIは整形するだけ）。担当お題（`answer_index`）は、主演本人にだけ brief / take / vote の間 `myAnswerIndex` で返し、`result` では全員に返します。代表者にも（主演でない限り）返しません。APIは、スナップショットに余計な答えが含まれていても `result` 前や主演以外には出さない作りです。
- 投票は件数だけを返します。自分の選択も返しません（`memberHasVoted` の真偽値だけ）。`result` のスナップショットには採点用に投票が含まれますが、APIは記号ごとの票数と正解者のID、そして呼び出した本人自身の結果（当たり／おしい／パス）だけを返し、ほかの人が何を選んだかは返しません。
- 区切りの振り返りは、そのラウンドの全テイクが終わった後なので、各テイクのお題を返します。パスしたテイクのお題は返しません。
- いいねは、自分が選んだ相手と全体の件数だけを返します。

## 同時操作

`revision` を要求するのは代表者の `start` だけです（遅れて参加した人を取りこぼさないため）。それ以外の `ready`・`skip`・`vote`・`next`・`like`・`close_vote`・`continue`・`finish` は `revision` を要求せず、`takeNo`（`like`・`continue` は `lapNo`）と phase で照合します。参加者の投票やいいねで `revision` が進んでも、代表者の「締め切る」「次のラウンドへ」「撮影終了」は失敗しません。押し遅れた操作は `ONE_CUT_STALE_TAKE` で拒否されます（`next` の二重押しの2回目など）。RPC が返す `ONE_CUT_INVALID` / `ONE_CUT_PARTICIPANTS`（名簿やお題の組が最新ではない）は、API で `GROUP_STALE`（409）に読み替えます。`one_cut_ready` は、API サーバーの時計と DB の時計が15秒以上ずれていても拒否せず、開始時刻を DB 側の「いまから1秒後」に置き換えます。`skip` は、skipped への更新と次テイクの作成を1回のRPC・1トランザクションで行い、途中で失敗するとskipごとロールバックします。

## 保存と期限

ルームへの参加情報を、そのルーム専用キーの `sessionStorage` へ保持します。お題・正解・票は端末へ保存しません。回答本文・ひとこと・顔の画像や音声を扱う機能（入力欄・カメラ・録音）はありません。

サーバーには、進行に必要なお題のスナップショット、テイク（6つのお題、担当お題）、投票、いいね、得点、主演賞だけを一時保持します。ゲームが終わった（`final` に入る）時点で、ゲームのデータをすぐ全部削除し、ルームは終了扱いになります。最後の結果画面を全端末に届けるため、全員の得点と主演賞だけを `one_cut_results` に `result_expires_at`（終了時刻＋5分）まで残し、その後は自動で削除します（`one_cut_state` が期限切れの行をその場で削除する他、既存のcleanupが過ぎた結果を削除します。cronは追加していません）。5分経過後の状態は `ended` の最小応答です。端末は一度受け取った結果をメモリに保持し、`ended` に変わっても表示を消しません（再読み込みすると見られません）。放置したルームは24時間後にアクセスできなくなり、物理削除は既存のcleanupで行われ、外部キーのcascadeで `one_cut_*`（`one_cut_results` を含む）も消えます。

次の順で、使い捨てDBに適用してから本番へ適用します。本番DBへ自動適用しません。

1. `supabase/migrations/202610080001_group_rooms.sql`（および既存のグループ関連migration）
2. `supabase/migrations/202610150001_minority_topic.sql`
3. `supabase/migrations/202610160001_question_wolf.sql`
4. `supabase/migrations/202610170001_group_game_types.sql`（`group_rooms.game_type` のCHECKを新ゲーム共通で張り替えます）
5. `supabase/migrations/202610170002_ochi_kara.sql`（別ゲーム。ワンカットは依存しませんが、共通の適用順に従います）
6. `supabase/migrations/202610170003_one_cut.sql`（このゲーム。CHECKは書き換えません。2回適用しても壊れません）

`one_cut_games`、`one_cut_takes`、`one_cut_votes`、`one_cut_likes`、`one_cut_results` は `service_role` 専用で、クライアントからの直接読み書きとRPC実行は拒否します。状態遷移はすべて `security definer` のRPC（`one_cut_create_room`、`one_cut_start_take`、`one_cut_to_break`、`one_cut_ready`、`one_cut_expire`、`one_cut_state`、`one_cut_cast_vote`、`one_cut_close_vote`、`one_cut_skip`、`one_cut_like`、`one_cut_close_break`、`one_cut_finish`）で行います。内部関数（`one_cut_member_order`、`one_cut_actor_ok`、`one_cut_finalize`、`one_cut_award_winners`、`one_cut_insert_take`、`one_cut_score_take`）はどのロールにも実行権限を付けません。追加のenvやAPIキーはありません。

後続フェーズ（F1スタート、全員同時撮影）の `mode` / `start_style` / `assignments` / `guesses` は初版から列を持たせ、`2026101800xx_*.sql` として別ファイルで RPC を差し替えます（初版の `one_cut_create_room` は `mode='solo_actor'`・`start_style='slate'` 以外を拒否します）。
